User's Guide
============


Introduction
------------

This pipeline converts nf-core/oncoanalyser WGS/WTS output and clinical
CSVs into cBioPortal-compatible import packages. It runs on HPC clusters
using SLURM and Apptainer (no Docker, no sudo).

The pipeline has three modes:

  Genomic mode   Processes per-subject oncoanalyser output (mutations,
                 copy-number, structural variants, gene expression, RNA
                 fusions, mutational signatures) and produces merged,
                 group-level cBioPortal data files packaged as a .tar.gz.

  Clinical mode  Transforms clinical CSVs (patient demographics, diagnoses,
                 treatments, specimens, etc.) into cBioPortal patient and
                 sample attribute files.

  Both mode      Runs genomic and clinical pipelines in a single invocation.
                 The genomic workflow runs first and generates a linking
                 file that maps sample IDs to clinical patient IDs. The
                 clinical workflow then runs automatically using that
                 linking file, so --sample_registrations is not needed.

Genomic mode processing steps:

  Step                         Input                        Output
  ---------------------------  ---------------------------  ----------------------------
  Copy-number variants         PURPLE somatic + gene TSVs   data_cna_hg38.seg,
                                                            data_cna_long.txt
  Structural variants (DNA)    PURPLE somatic SV VCF        data_sv.txt (DNA rows)
  RNA fusions                  Isofox pass_fusions TSV      data_sv.txt (RNA rows)
  Gene expression              Isofox gene_data TSV         data_expression.txt
  Mutations                    PURPLE somatic/germline +    data_mutations_dna_rna_
                               SAGE RNA-append VCFs         germline.txt (MAF)
  Mutational signatures (SBS)  SNV trinucleotide counts     Contribution + counts
  Mutational signatures (DBS)  PURPLE somatic VCF           Contribution + counts
  Mutational signatures (ID)   PURPLE somatic VCF           Contribution + counts
  TMB / TML / HRD              PURPLE purity TSV, CHORD     data_clinical_sample.txt
                               prediction TSV               (columns; see output.txt)
  ML feature tables            Merged group-level files     ML-formatted CNV, expression,
  (only with --run_ml)                                      mutation, SV

DNA SVs and RNA fusions share the same data_sv.txt file; they are
distinguished by DNA_Support / RNA_Support flags and the Class column
(DELETION/DUPLICATION/INVERSION/TRANSLOCATION for DNA, FUSION for RNA).

Incremental processing:

  The pipeline detects already-processed subjects by checking for existing
  output files. Subjects with all expected outputs are skipped automatically,
  allowing you to add new subjects to the samplesheet and re-run without
  reprocessing the entire cohort.


Prerequisites
-------------

Software:

  Software      Version     Notes
  ----------    --------    ----------------------------------------
  Nextflow      >= 26.04.4  module load nextflow/26.04.4 on most HPC
  Apptainer     >= 1.0      Required for containers. Not Docker.
  htslib        Any recent  Provides bcftools and tabix

Container images:

  Five Apptainer containers are used. They are pulled automatically on
  first run and cached in containers/:

  Container                      Purpose
  -----------------------------  ----------------------------------------
  sdp-r:4.5.1                    R scripts (CNV, SV, expression, aggregation)
  sdp-python:3.12                Python scripts
  mafsmith-fastvep:0.1.0-0.4.0   VCF-to-MAF conversion (mafsmith + fastVEP)
  pcgr:2.2.5                     Germline variant annotation (PCGR/CPSR)
  sigprofiler:1.1.3              Mutational signature fitting

  GHCR authentication: Containers at ghcr.io/crchum-citadel require
  membership in the crchum-citadel GitHub organization and a PAT:

    apptainer registry login --username <github_username> oras://ghcr.io

Reference data:

  All reference files ship in one download, the resource kit
  (nextflow-cbioportal-resources-v1.0.0.tar.gz). Extract it and pass:

    --resources_dir /path/to/nextflow-cbioportal-resources-v1.0.0

  Any reference param set explicitly overrides the kit for that file.
  COSMIC fusions (cosmic_data) are licence-gated and not in the kit;
  they are only read with --run_ml, and leaving cosmic_data empty skips
  the ML SV step. Kit contents and
  layout: docs/resources.md.

  Offline HPC nodes: Set NXF_OFFLINE=true and pre-pull all containers
  on a login node before submitting jobs:

    apptainer pull --dir containers/ oras://ghcr.io/crchum-citadel/sdp-r:4.5.1


Preparing input data
--------------------

GENOMIC SAMPLESHEET

  The genomic samplesheet is a CSV with one row per subject.

  Column       Required  Description
  -----------  --------  ----------------------------------------
  group        Yes       Study/cohort identifier (no spaces)
  subject_id   Yes       Patient/subject identifier
  sample_id    Yes       Sample base name used in output filenames
  folder       Yes       Absolute path to oncoanalyser output dir

  Example:

    group,subject_id,sample_id,folder
    COHORT1,PATIENT1,SAMPLE1,/data/oncoanalyser_output/COHORT1/PATIENT1
    COHORT1,PATIENT2,SAMPLE2,/data/oncoanalyser_output/COHORT1/PATIENT2
    COHORT2,PATIENT3,SAMPLE3,/data/oncoanalyser_output/COHORT2/PATIENT3

  Expected folder layout:

    Each subject's folder must contain oncoanalyser output as follows.
    All modalities are optional -- missing or empty files are skipped.

    <folder>/
    |-- sage_append/
    |   +-- <subject_id>-T/
    |       +-- <subject_id>-T.sage.append.vcf.gz      RNA-supported somatic
    |-- purple/
    |   |-- <subject_id>-T.purple.somatic.vcf.gz       Somatic DNA mutations
    |   |-- <subject_id>-T.purple.germline.vcf.gz      Germline DNA mutations
    |   |-- <subject_id>-T.purple.sv.vcf.gz            Somatic structural variants
    |   |-- <subject_id>-T.purple.cnv.somatic.tsv      Somatic CN segments
    |   |-- <subject_id>-T.purple.cnv.gene.tsv         Gene-level copy numbers
    |   +-- <subject_id>-T.purple.purity.tsv           Sex (chrX/chrY), TMB/TML
    |-- chord/
    |   +-- <subject_id>-T.chord.prediction.tsv        HRD score/status/type
    |-- isofox/
    |   |-- <subject_id>-T.isf.gene_data.tsv           Gene expression (Isofox)
    |   +-- <subject_id>-T.isf.pass_fusions.tsv        RNA gene fusions (Isofox)
    +-- sigs/
        +-- <subject_id>-T.sig.snv_counts.csv          Trinucleotide SNV counts

    File naming: The pipeline resolves files using subject_id (from the
    samplesheet), not sample_id. For example, if subject_id=PATIENT1,
    the pipeline looks for PATIENT1-T.purple.somatic.vcf.gz.

CLINICAL SAMPLESHEET

  The clinical samplesheet is a CSV pointing to individual clinical
  data files.

  Column           Required  Description
  ---------------  --------  ----------------------------------------
  group_id         No        Group/study identifier
  filetype         Yes       Data type (see below)
  filepath         Yes       Path to clinical CSV file
  extraction_date  Yes       Date data was extracted (YYYY-MM-DD)
  info             No        Additional information

  Supported filetypes (ARGO/ICGC-ARGO format):

    donors, primary_diagnoses, treatments, surgeries, systemic_therapies,
    specimens, radiations, follow_ups, sample_registrations, biomarkers

  Dates in clinical CSVs are stored as day/month intervals relative to
  diagnosis (day 0): {"day_interval": N, "month_interval": M}

  Example:

    group_id,filetype,filepath,extraction_date,info
    COHORT1,donors,/data/clinical/donors.csv,2025-05-20,
    COHORT1,primary_diagnoses,/data/clinical/primary_diagnoses.csv,2025-05-20,
    COHORT1,treatments,/data/clinical/treatments.csv,2025-05-20,
    COHORT1,surgeries,/data/clinical/surgeries.csv,2025-05-20,
    COHORT1,systemic_therapies,/data/clinical/systemic_therapies.csv,2025-05-20,
    COHORT1,specimens,/data/clinical/specimens.csv,2025-05-20,
    COHORT1,radiations,/data/clinical/radiations.csv,2025-05-20,
    COHORT1,follow_ups,/data/clinical/follow_ups.csv,2025-05-20,
    COHORT1,sample_registrations,/data/clinical/sample_registrations.csv,2025-05-20,
    COHORT1,biomarkers,/data/clinical/biomarkers.csv,2025-05-20,

SAMPLE REGISTRATIONS FILE (optional, template mode only)

  A sample_registrations.csv used to generate minimal clinical files when
  no clinical_samplesheet is provided. The pipeline keeps sample_type=Total DNA
  rows with tumour_normal_designation=Tumour to derive the patient → sample
  mapping. Germline normals (Buffy coat, Whole blood, ...) are patient-level
  context only and are never emitted as samples.

    program_id,sample_type,specimen_tissue_source,...,submitter_donor_id,submitter_sample_id,tumour_normal_designation
    PROG,Total DNA,Solid tissue,...,PATIENT1,PATIENT1-1DT,Tumour
    PROG,Total DNA,Buffy coat,...,PATIENT1,PATIENT1-1DN,Normal
    PROG,Total DNA,Solid tissue,...,PATIENT2,PATIENT2-1DT,Tumour

  Pass via --sample_registrations path/to/sample_registrations.csv.

GENERATING A SAMPLESHEET

GENOMIC SAMPLESHEET

  For oncoanalyser WGS/WTS output (directories ending in _WGTS):

    python3 bin/generate_samplesheet.py /path/to/oncoanalyser_output \
        -o samplesheet.csv

    Scans the input directory for *_WGTS/ folders and produces a CSV
    with columns: group, subject_id, sample_id, folder.

  For DRAGEN DNA/RNA output (directories with dna/ and rna/ subfolders):

    python3 create_samplesheet.py --input_dir /path/to/dragen_output

    Expects a directory containing dna/ and rna/ subfolders with
    standard DRAGEN output. Produces samplesheet.csv with columns:
    group_id, subject_id, sample_id, sample_type, sequence_data,
    info, filepath. Creates 3 rows per subject (DT somatic DNA,
    DN germinal DNA, RT somatic RNA).

CLINICAL SAMPLESHEET

  Use generate_clinical_samplesheet.py to build the clinical samplesheet
  from a directory of ARGO/ICGC-ARGO CSV files:

    python3 bin/generate_clinical_samplesheet.py /path/to/clinical_dir \
        -o clinical_samplesheet.csv \
        -d 2025-05-20 \
        --study_id MY_COHORT

  Options:

    input_dir          Directory containing clinical CSV files.
    -o / --output      Output path (default: clinical_samplesheet.csv).
    -d / --date        Extraction date in YYYY-MM-DD format (default: today).
    --study_id         Value written to the group_id column (default: empty).
    --relative-to DIR  Write file paths relative to DIR instead of absolute.
                       Use this when the samplesheet will be kept next to
                       the pipeline directory (set DIR to the project root).

  The script matches files by name stem to the 10 supported filetypes:

    donors.csv              primary_diagnoses.csv   treatments.csv
    surgeries.csv           systemic_therapies.csv  specimens.csv
    radiations.csv          follow_ups.csv          sample_registrations.csv
    biomarkers.csv

  Unrecognised CSV files are skipped with a warning. Only files that
  are present in the directory are included; you do not need all 10.

  Example — writing relative paths for a samplesheet stored in the
  project directory alongside the pipeline:

    python3 bin/generate_clinical_samplesheet.py /data/argo_extract \
        -o clinical_samplesheet.csv \
        -d 2025-08-01 \
        --study_id COHORT2025 \
        --relative-to /path/to/nextflow-cbioportal/oncoanalyser

  To verify the generated samplesheet works end-to-end, run:

    python3 -m pytest tests/test_generate_clinical_samplesheet.py -v


Configuration reference
-----------------------

All parameters are set in nextflow.config or overridden on the command
line with --param_name value.

The pipeline prints its own parameter reference from nextflow_schema.json:

    nextflow run main.nf --help              # main parameters, by group
    nextflow run main.nf --help resources_dir  # full help for one parameter
    nextflow run main.nf --help --showHidden # include the kit-file overrides

  Nextflow reports the help run as cancelled (exit status 1); that is
  how the nf-schema plugin stops after printing, not an error.

CORE PARAMETERS

  Parameter              Required  Default                   Description
  ---------------------  --------  ------------------------  ----------------------
  mode                   Yes       genomic                   genomic, clinical, or both
  study_id               Yes       --                        Study identifier for meta_study.txt and output folder
  project_description    Yes       --                        Study description
  outdir                 No        output_<project>_<date>   Output directory

GENOMIC INPUT PARAMETERS

  Parameter                Required  Default   Description
  -----------------------  --------  --------  ----------------------------
  genomic_samplesheet      Yes       --        Path to genomic samplesheet CSV
                                               (optional in clinical mode: keeps
                                               only its subjects)
  resources_dir            Yes       --        Extracted resource kit (all reference files)
  mafsmith_retain_ann      No        (10 CSQ)  Extra VEP fields kept as MAF columns
  germline_min_depth       No        10        Min normal DP to infer a germline GT
  germline_het_min_vaf     No        0.2       Min normal AF for 0/1; below it is 0/0
  germline_hom_min_vaf     No        0.9       Min normal AF for 1/1
  run_ml                   No        false     Also build the ML feature tables (machine_learning/)
  cosmic_data              No        --        COSMIC Fusion TSV for ML (licence-gated)

  A single kit file can be overridden by its param name (docs/resources.md).

CLINICAL INPUT PARAMETERS

  Parameter                         Required  Default        Description
  --------------------------------  --------  -----------    ----------------------------
  clinical_samplesheet              Yes*      --             Path to clinical samplesheet CSV
  sample_registrations              Yes*      (empty)        sample_registrations.csv for template mode

  * Clinical mode needs one of the two. Both mode needs neither: without
    a clinical samplesheet it builds the template from the genomic
    linking file.

  MOHCCN mapping tables come from resources_dir.

Running the pipeline
--------------------

PROFILES

  Always include the apptainer profile. Combine with others as needed.

  Profile      Purpose
  -----------  ------------------------------------------------
  apptainer    REQUIRED. Enables Apptainer. Images are cached in
               containers/ unless a site config sets apptainer.cacheDir.
  slurm        Submits jobs to SLURM. Set clusterOptions for
               your allocation (see SITE CONFIGURATION below).
  citadel      CRCHUM/CITADEL site settings: resource kit location,
               prebuilt .sif containers, SLURM account, scratch and
               Apptainer cache. List it LAST. It does not set outdir
               or email; put those in a -params-file.
  debug        Dumps process hashes, prints hostname, keeps work dir.
  local        Uses local SIF paths instead of ORAS URIs.
  test         Uses bundled test data with reduced resources.


SITE CONFIGURATION

  At CRCHUM, add the citadel profile (list it LAST). It sets the kit
  location, cosmic_data, containers and the SLURM account:

    nextflow run main.nf -profile slurm,apptainer,citadel ...

  Elsewhere, pass the kit yourself:

    nextflow run main.nf -profile apptainer \
      --mode genomic \
      --genomic_samplesheet samplesheet.csv \
      --resources_dir /path/to/nextflow-cbioportal-resources-v1.0.0

  or copy nextflow_citadel.config as a template and pass it with -c.

  mafsmith reference data

    Use the kit's mafsmith home. It ships its own fastVEP (0.3.0),
    which mafsmith uses instead of the container's.

  MAF columns

    mafsmith writes 53 standard MAF columns where vcf2maf wrote ~133,
    so the VEP annotations cBioPortal displays are opt-in. VEP packs
    them into the VCF's INFO/CSQ field and declares the layout in the
    header ("... Format: Allele|Consequence|IMPACT|..."); mafsmith's
    --retain-ann names subfields to pull out and append as extra MAF
    columns, in the order given.

    mafsmith_retain_ann drives that flag. Its default is

      Consequence,IMPACT,SYMBOL,Feature_type,CCDS,EXON,INTRON,
      Existing_variation,CLIN_SIG,AF

    Names must match fastVEP's CSQ field list exactly. A name fastVEP
    does not emit is not an error -- you get a column of empty strings.
    The full list fastVEP writes is its DEFAULT_CSQ_FIELDS: Allele,
    Consequence, IMPACT, SYMBOL, Gene, Feature_type, Feature, BIOTYPE,
    EXON, INTRON, HGVSc, HGVSp, cDNA_position, CDS_position,
    Protein_position, Amino_acids, Codons, Existing_variation,
    REF_ALLELE, UPLOADED_ALLELE, DISTANCE, STRAND, FLAGS, CANONICAL,
    SYMBOL_SOURCE, HGNC_ID, MANE, MANE_SELECT, MANE_PLUS_CLINICAL, TSL,
    APPRIS, CCDS, ENSP, SOURCE, HGVS_OFFSET, SIFT, PolyPhen, AF,
    CLIN_SIG, SOMATIC, PHENO, PUBMED, MOTIF_NAME, MOTIF_POS,
    HIGH_INF_POS, MOTIF_SCORE_CHANGE, TRANSCRIPTION_FACTORS, ACMG,
    ACMG_CRITERIA. Some of these (Allele, Gene, Feature, BIOTYPE,
    CANONICAL, SIFT, PolyPhen, HGVSc, HGVSp) are already standard MAF
    columns and do not need retaining.

    vcf2maf's RefSeq and VARIANT_CLASS have no fastVEP counterpart and
    cannot be restored this way. Set mafsmith_retain_ann to "" to drop
    back to the 53 standard columns.

  Germline genotypes

    Germline calls come from PURPLE's germline VCF. FILTER_GERMLINE_DNA
    keeps records whose FILTER is exactly PASS or LOW_TUMOR_VCN (a
    tumour-side flag: the call in the normal is real) and drops LOW_VAF
    and everything else, including LOW_TUMOR_VCN;LOW_VAF.

    PURPLE sets GT (0/1, 1/1) where it can and leaves ./. elsewhere;
    CPSR drops uncalled genotypes. PURPLE's calls are kept as-is, and
    only the ./. ones are inferred from the normal's FORMAT/DP and
    FORMAT/AF (bcftools +setGT):

      DP >= 10 and AF >= 0.9         1/1
      DP >= 10 and 0.2 <= AF < 0.9   0/1
      AF < 0.2 (any depth)           0/0, treated as noise and removed
      DP < 10 and AF >= 0.2          stays ./. (CPSR drops it)

    The 0/0 records are removed before CPSR because CPSR 2.2.5 keeps
    and classifies them; only CPSR 2.3 and later drop them itself.

    Setting low-AF sites to reference assumes no tumour-in-normal
    contamination: with heavy contamination a somatic variant can
    pass 0.2 in the normal and be reported as a germline het. The
    cutoffs are germline_min_depth, germline_het_min_vaf and
    germline_hom_min_vaf.

GENOMIC MODE

  module load nextflow/26.04.4 apptainer/1.3.5 htslib/1.22.1

  nextflow run main.nf \
      -profile slurm,apptainer,citadel \
      --mode genomic \
      --study_id "MY_STUDY" \
      --project_description "Description of my study" \
      --genomic_samplesheet samplesheet.csv

CLINICAL MODE

  Builds only the clinical part of a study from ARGO/ICGC-ARGO CSVs.
  No oncoanalyser output, genomic samplesheet, genome reference or
  genomic container is needed, and no genomic task runs.

  nextflow run main.nf \
      -profile slurm,apptainer,citadel \
      --mode clinical \
      --study_id "MY_STUDY" \
      --clinical_samplesheet clinical_samplesheet.csv

  Outside CRCHUM, replace citadel with --resources_dir: the three
  MOHCCN mapping tables come from the resource kit.

  nextflow run main.nf \
      -profile apptainer \
      --mode clinical \
      --study_id "MY_STUDY" \
      --clinical_samplesheet clinical_samplesheet.csv \
      --resources_dir /path/to/nextflow-cbioportal-resources-v1.0.0

  Required:

    --study_id              Names the output folder <outdir>/<study_id>/
                            and the cancer_study_identifier in every meta
                            file (lower-cased, '-' becomes '_'). The run
                            stops without it. Use the same value as the
                            genomic run the clinical data belongs to.
    --clinical_samplesheet  or --sample_registrations (see below). The
                            run stops if neither is given.

  The group_id column of the clinical samplesheet is not used for
  naming; --study_id decides. Relative filepath values in the
  samplesheet resolve against the pipeline directory, not the
  directory you launch from -- prefer absolute paths.

  Output, in <outdir>/<study_id>/:

    data_clinical_patient.txt, meta_clinical_patient.txt
    data_clinical_sample.txt,  meta_clinical_sample.txt
    data_timeline.txt,         meta_timeline.txt  (when event data exists)

  By default every Total DNA / Tumour / Solid tissue sample in
  sample_registrations becomes a row.

  Restricting to genomic samples (optional): add --genomic_samplesheet
  to output clinical data only for the subjects it lists, exactly as
  both mode does with its linking file:

    nextflow run main.nf \
        -profile slurm,apptainer,citadel \
        --mode clinical \
        --study_id "MY_STUDY" \
        --clinical_samplesheet clinical_samplesheet.csv \
        --genomic_samplesheet samplesheet.csv

    - Only subject_id and sample_id are read. The folder column is not
      opened, so no oncoanalyser output is needed and no genomic task
      runs.
    - Every clinical output -- patient, sample and timeline -- keeps
      only subjects whose subject_id is in the samplesheet. The run
      fails if none match.
    - A subject with one tumour sample takes the samplesheet's
      sample_id as SAMPLE_ID, so it matches the genomic files. A
      subject with several keeps its clinical sample IDs.
    - Per-subject slices <study_id>/<subject>/<sample_id>.data_clinical_
      {sample,patient}.txt are written, as in both mode.
    - Also applies to the template variant below.

  Pass the same samplesheet the genomic run used: the result then
  matches what --mode both would have written. Note -profile test sets
  genomic_samplesheet, so a clinical run under it is filtered.

  Template variant (no clinical CSVs): pass --sample_registrations
  instead of --clinical_samplesheet to get a minimal
  data_clinical_sample.txt (PATIENT_ID, SAMPLE_ID, SAMPLE_TYPE=Primary)
  plus its meta file. No patient or timeline file is written.

  nextflow run main.nf \
      -profile slurm,apptainer,citadel \
      --mode clinical \
      --study_id "MY_STUDY" \
      --sample_registrations /data/clinical/sample_registrations.csv

  Loading the output: clinical mode writes no meta_study.txt,
  cancer_type.txt, case lists or .tar.gz, so its folder is not a
  standalone study. Pair it with a genomic run instead:

    1. Run --mode genomic with --study_id MY_STUDY --outdir results.
    2. Run --mode clinical with the same --study_id and --outdir, and
       --genomic_samplesheet set to step 1's samplesheet. The
       clinical files land in results/MY_STUDY/ next to the genomic
       ones (a genomic-only run writes no clinical files, so nothing
       is overwritten).
    3. Validate and import results/MY_STUDY/ as described in
       docs/output.txt. Note the genomic run's MY_STUDY.tar.gz does
       not contain the clinical files; import the folder, or use
       --mode both to get one archive with everything.

  To refresh the clinical data of an already-loaded study, rerun
  step 2 with updated CSVs and re-import the folder.

BOTH MODE

  Runs genomic and clinical pipelines together. The linking file is
  generated automatically by the genomic workflow and passed to the
  clinical workflow, so --sample_registrations is not needed.

  nextflow run main.nf \
      -profile slurm,apptainer,citadel \
      --mode both \
      --study_id "MY_STUDY" \
      --project_description "Description of my study" \
      --genomic_samplesheet samplesheet.csv \
      --clinical_samplesheet clinical_samplesheet.csv

USING A PARAMS FILE

  Instead of passing every parameter on the command line, create a
  YAML file:

    # params.yaml
    mode: "genomic"
    study_id: "MY_STUDY"
    project_description: "Description of my study"
    genomic_samplesheet: "/data/samplesheet.csv"
    resources_dir: "/path/to/nextflow-cbioportal-resources-v1.0.0"
    cosmic_data: "/path/to/Cosmic_Fusion_v103_GRCh38.tsv"
    outdir: "output_my_study"
    email: "user@example.com"

  Then run:

    nextflow run main.nf -profile slurm,apptainer,citadel -params-file params.yaml

  Note: Use -params-file (not -c) for parameters. Custom config files
  via -c should only be used for process resource tuning.

LOCAL EXECUTION (no SLURM)

  nextflow run main.nf -profile apptainer \
      --mode genomic \
      --genomic_samplesheet samplesheet.csv

RUNNING VIA NEXTFLOW CONTAINER

  If Nextflow is not installed, run it inside an Apptainer container:

    apptainer pull --dir containers/ oras://ghcr.io/crchum-citadel/sdp-nextflow:25.04.7

    apptainer exec containers/sdp-nextflow_25.04.7.sif \
        nextflow run main.nf -profile apptainer \
        --mode genomic \
        --genomic_samplesheet samplesheet.csv

RESUMING A FAILED RUN

  Nextflow caches intermediate results. If a run fails, fix the issue
  and resume:

    nextflow run main.nf -profile slurm,apptainer,citadel -params-file params.yaml -resume

  Nextflow reuses cached results from completed steps and only re-runs
  what failed. The pipeline's incremental processing also skips subjects
  that already have all expected output files.

RUNNING TESTS

  Verify your installation with the bundled test data:

    ./nf-test test tests/ --profile test,apptainer

  Or a subset -- the clinical pipeline tests, for example:

    ./nf-test test tests/clinical.nf.test tests/clinical_generated.nf.test \
        tests/clinical_template.nf.test tests/both.nf.test \
        --profile test,apptainer

    ./nf-test test tests/subworkflows/genomic_cnv.nf.test \
        --profile test,apptainer

  Regenerate snapshots after an intended output change:

    ./nf-test test <test> --profile test,apptainer --update-snapshot

  CI runs with --ci --changed-since HEAD^, which never updates snapshots,
  so commit any snapshot change together with the change that caused it.

  The Python suites (samplesheet generator, output combiner) run under
  pytest:

    python3 -m pytest tests/ -v


Troubleshooting
---------------

CONTAINER PULL FAILURES

  Symptom: "FATAL: Unable to pull from ORAS" or authentication errors.

  Fix: Log in to GHCR on the node that pulls containers:

    apptainer registry login --username <github_username> oras://ghcr.io

  For offline compute nodes, pre-pull on a login node:

    apptainer pull --dir containers/ oras://ghcr.io/crchum-citadel/sdp-r:4.5.1
    # Repeat for all 5 containers

VEP/PCGR DOWNLOAD FAILURES

  Symptom: VEP or PCGR steps fail trying to download reference data.

  Fix: Use the resource kit (--resources_dir), which carries the VEP
  cache and PCGR bundle; the downloads only run when neither the kit
  nor vep_data / pcgr_data supplies them.

SLURM ACCOUNT ERRORS

  Symptom: "sbatch: error: invalid account" or similar.

  Fix: At CRCHUM, add the citadel profile, which sets the account:

    nextflow run main.nf -profile slurm,apptainer,citadel ...

  Elsewhere, set clusterOptions to your own allocation in your site
  config (see SITE CONFIGURATION) rather than editing nextflow.config:

    process.clusterOptions = '--account=your-allocation'

"ALL SUBJECTS IN SAMPLESHEET ALREADY PROCESSED"

  Symptom: Pipeline exits saying all subjects are already processed.

  Cause: Incremental processing found all expected outputs for every
  subject.

  Fix: Either (a) delete the output directory, (b) remove processed
  subjects from the samplesheet, or (c) add new unprocessed subjects.

EXPRESSION MERGE REQUIRES 2+ SAMPLES

  Symptom: Warning about needing at least 2 files to merge.

  Cause: cBioPortal expression files require 2+ samples per group.

  Fix: Add more subjects, or accept that expression won't be generated
  for single-sample groups.

MEMORY OR TIME ERRORS

  The pipeline uses process labels for resource limits (conf/base.config):

    Label                CPUs  Memory   Time
    -------------------  ----  -------  -----
    process_single       1     6 GB     4 h
    process_low          2     12 GB    4 h
    process_medium       6     36 GB    8 h
    process_high         12    72 GB    16 h
    process_high_memory  --    200 GB   --

  Processes with error_retry retry up to 3 times. To increase resources
  for a specific process, create a custom config:

    // custom.config
    process {
        withName: 'MAFSMITH' {
            memory = '100.GB'
            time   = '24.h'
        }
    }

  Then pass it with -c custom.config.

MISSING INPUT FILES

  Symptom: Warnings like "File not found for PATIENT1 (mutation ...)"

  Cause: Expected file does not exist in the subject's output folder.

  Fix: Check the folder layout matches the expected structure above.
  Missing files are skipped -- the pipeline processes available modalities.

NEXTFLOW MEMORY

  If Nextflow itself runs out of memory:

    export NXF_OPTS='-Xms1g -Xmx4g'

RUNNING IN THE BACKGROUND

  Use screen, tmux, or submit Nextflow itself as a SLURM job:

    screen -S nf-run
    nextflow run main.nf -profile slurm,apptainer,citadel -params-file params.yaml
    # Ctrl+A, D to detach; screen -r nf-run to reattach
